# Policy and environment parity

This repository validates the policy-facing Microduck contract at two boundaries:

1. a deterministic native MuJoCo fixture for the local BAM implementation; and
2. an optional paired rollout against the `microduck_rl` MuJoCo-Warp velocity task.

These checks compare explicit arrays and configuration metadata. They do not imply that different
contact solvers produce bit-identical contact manifolds.

## Deployment policy

The default policy is `alpha_walking.onnx` from the public
[`pollen-robotics/microduck-policies`](https://huggingface.co/pollen-robotics/microduck-policies)
repository:

| Contract | Value |
| --- | --- |
| Input | 61 actor observations |
| Output | 14 deployment actions |
| Control rate | 50 Hz |
| Format | ONNX |

`microduck-fetch-policy` resolves a policy name through the repository manifest, downloads the
manifest and ONNX file at a pinned Hub revision, and validates the robot identifier, dimensions,
control rate, graph dimensions, and SHA-256 digest. The resulting `PolicyArtifact` carries that
provenance; downloaded sets also contain a small `download.json` record.

The policy loader does not select a task or alter its configuration. The rollout caller connects
the policy to the environment explicitly:

```python
from microduck_rl_torch.envs import ManagerBasedTaskEnv
from microduck_rl_torch.policies import OnnxPolicy, fetch_policy
from microduck_rl_torch.tasks import make_microduck_velocity_env_cfg

artifact = fetch_policy("alpha_walking")
policy = OnnxPolicy(artifact)
env = ManagerBasedTaskEnv(make_microduck_velocity_env_cfg())
try:
    observation = env.reset()
    for _ in range(250):
        transition = env.step(policy(observation))
        observation = transition.observation
        if transition.terminated or transition.truncated:
            break
finally:
    env.close()
```

The public artifact is a deployment policy, not a trainer checkpoint. Loading an arbitrary PyTorch
checkpoint would not establish parity without its network architecture, observation normalization,
action scaling, task configuration, and run metadata.

## Local BAM fixture

The policy-facing environment uses the Microduck walk XML, BAM M6 actuator behavior, a 0.005 s
physics timestep, and four physics steps per 50 Hz action. The configured observation and reward
terms include command, base-state, joint-state, action-history, and velocity-task values with the
documented delay and history behavior.

The tracked fixture at `tests/fixtures/microduck_bam_golden.npz` is generated by the independent
MuJoCo C reference. It disables contacts so the comparison isolates actuation, integration,
observations, rewards, and termination. Contact-enabled execution has finite-path coverage, but
native and Torch contact manifolds are not treated as the same numerical reference.

The rendering CLI supports both actuator modes. Its default XML mode is the visual regression path;
`RENDER_ACTUATOR_MODE=bam` selects the BAM configuration used for actuator parity. Both modes share
the same scene, task, observation, and rendering interfaces.

## `microduck_rl` MuJoCo-Warp rollout

`scripts/validate_warp_parity.py` runs a paired 500-step comparison with the
`mjlab_microduck` `Mjlab-Velocity-Flat-MicroDuck` task. It launches
[`scripts/run_microduck_rl_warp_rollout.py`](../scripts/run_microduck_rl_warp_rollout.py) in the
`microduck_rl` interpreter and source tree, so the reference process does not import the local
Torch environment.

Both sides use the same 61-to-14 ONNX policy, seed, flat walk model, fixed command, and 50 Hz
control schedule. The deterministic comparison disables reset/interval randomization, command
resampling, actor observation corruption, domain randomization, and actuator-delay randomization.
It retains fixed BAM voltage/friction values and the one-tick joint-velocity observation delay.

Run it with:

```bash
make install-microduck-rl-warp
make warp-parity \
  MICRODUCK_RL_ROOT=/path/to/microduck_rl \
  MICRODUCK_RL_PYTHON=/path/to/microduck_rl/.venv/bin/python
```

The report contains cumulative maximum absolute differences for action, actor observation, `qpos`,
and `qvel` at control steps `1, 5, 10, 25, 50, 100, 250, 500`, plus the exact policy and
`microduck_rl` revisions used. `MICRODUCK_RL_DEVICE` selects the reference device. A compatible
MuJoCo-Warp runtime is required; there is no MPS backend. The selected `--fail-on` threshold
controls the command exit status, and `WARP_PARITY_FAIL_ON=none` produces a diagnostic report
without failing on metric thresholds.
