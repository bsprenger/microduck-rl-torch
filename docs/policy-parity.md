# Policy parity notes

The initial golden artifact is `alpha_walking.onnx` from the official public model repository:

- repository: `pollen-robotics/microduck-policies`
- policy API: 61 observations to 14 actions
- deployment frequency: 50 Hz
- model format: ONNX

The repository manifest is fetched at the same resolved revision as the policy. The fetcher checks
the model API dimensions, robot identifier, control frequency, ONNX graph dimensions, and SHA-256
digest. It then writes a small local artifact metadata file alongside the policy.

This is intentionally a deployment-level golden policy rather than a raw trainer checkpoint. The
upstream Hugging Face Jobs flow uploads `logs/rsl_rl/**/model_*.pt` snapshots to private model
repositories. A future checkpoint adapter should be added only after the exact run configuration,
network architecture, observation normalization, and action scaling are identified; loading an
arbitrary `.pt` file would not establish parity.

The policy-facing environment uses the upstream walk XML with the BAM M6 XL330 actuator model:
the firmware P controller, DC-motor back-EMF, load-dependent friction budget, stiff friction
constraints, 0.005 s physics timestep, and four physics steps per 50 Hz policy action. Backlash
models use output-side position/velocity observations and output-side position feedback while
retaining motor-side back-EMF. Reset randomization, command buckets, delayed observations,
termination, and the configured velocity-task reward terms are represented explicitly in the
Torch environment.

The visual golden-rollout command has an explicit actuator-mode switch. Its default is the XML
position-actuator path used by the pre-refactor alpha-walking video, so the artifact remains a
reproducible deployment/regression view. `RENDER_ACTUATOR_MODE=bam` exercises the BAM path used by
the upstream parity task. These paths share the same scene, task composition, observation, and
rendering machinery; selecting XML for the visual regression does not remove BAM support.

The exact regression fixture is generated by the independent MuJoCo C reference and stored at
`tests/fixtures/microduck_bam_golden.npz`. It intentionally disables contacts: this isolates
actuation, integration, observations, rewards, and termination from the known difference between
the local pure-Torch plane/mesh contact approximation and MuJoCo C's mesh contact manifold. The
contact-enabled environment still has a finite-path integration test; native contact manifolds
must not be called numerically identical until that backend gap is closed.

## Upstream-Warp rollout parity

`scripts/validate_warp_parity.py` is the environment parity check against the actual upstream
`mjlab_microduck` `Mjlab-Velocity-Flat-MicroDuck` task. It launches
`scripts/run_upstream_warp_rollout.py` in a separately provisioned upstream interpreter, rather
than importing the local Torch environment into the reference process. Both sides use the same
61-to-14 ONNX policy, fixed command, seed, flat walk model, and 50 Hz control schedule.

The default report has cumulative maximum-absolute-error rows at control steps
1, 5, 10, 25, 50, 100, 250, and 500. It compares the policy action, the actor observation fed to
the policy, and the post-step generalized position and velocity. Upstream reset/interval events,
domain randomization, actor corruption, command resampling, and the BAM actuator delay are
disabled for this deterministic diagnostic; fixed BAM voltage/friction defaults and the
observation-side one-tick joint-velocity delay remain enabled on both implementations.

Run it with:

```bash
make warp-parity \
  UPSTREAM_ROOT=/path/to/microduck_rl \
  UPSTREAM_PYTHON=/path/to/upstream/.venv/bin/python
```

The upstream reference stack is an optional dependency group so the normal CPU-first install stays
small. Install it with `make install-upstream`; a machine with a compatible `mjlab`/MuJoCo-Warp
runtime (normally a CUDA-capable environment) is still required to execute this check. If that
runtime is missing, the command writes an error report instead of silently falling back to the
native MuJoCo fixture.

The local `mujoco-torch` dependency is pinned to the sibling checkout so its solver, collision,
and renderer fixes are immediately used after `uv sync --reinstall-package mujoco-torch`.

The target keeps the full CAD mesh arrays for rendering but only derives convex collision data for
geoms enabled by MuJoCo contact masks or explicit pairs. This matches the upstream separation of
visual and curated collision geometry. The default CPU smoke command still disables contact
processing for a bounded quick check; `CONTACTS=enabled` runs the curated contact path.
